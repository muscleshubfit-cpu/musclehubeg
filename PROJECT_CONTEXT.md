## 1. Product Identity

**MuscleHubEG** (publicly branded **MuscleHub**) is a bilingual
(Arabic / English) fitness, nutrition, and coaching platform. The
primary audience is the Egyptian / Gulf Arabic-speaking market, with
English as the secondary interface language.

The product offers:

- A library of **868+ exercises** (sourced from the open-source
  `yuhonas` exercise dataset, images hosted on GitHub).
- A food database of **8,830+ foods** with per-100g macros.
- **6 free tools**: Calorie calculator, BMI, Macros, Body-Fat %,
  Water tracker, Meal Planner.
- **EVO AI Coach** — a floating chat widget powered by OpenRouter's
  free model tier, with a local rule-based fallback.
- A **blog CMS** with automated AI article generation (3-step cron
  pipeline) and manual coach-driven generation.
- A **coach dashboard** for client management, payment review
  (InstaPay / Vodafone Cash receipts), and support tickets.
- **4 membership tiers**: Free, Premium ($14.99/mo), Pro ($29.99/mo),
  Coaching ($39.99/mo). Multiple memberships are allowed (e.g. a
  client can hold Coaching + Premium simultaneously — migration 0011).
- A **referral system** with 20% commission tracking.
- PWA support (manifest + service worker).

Live deployment: `https://musclehubeg.vercel.app` (Vercel, `sin1`
region).

```

   ↓

   ↓

   ↓

```

### 4.3 Key Architectural Decisions

1. **Dual-mode data layer**: `src/lib/data.ts` works against Supabase
   in production, and falls back to `localStorage` "demo mode" when
   Supabase env vars are missing. This lets the UI be exercised
   without a backend.
2. **Cookie-based auth via middleware**: `src/middleware.ts` uses
   `@supabase/ssr`'s `createServerClient` to sync the PKCE verifier
   to cookies so the server-side `/auth/callback` route can exchange
   the OAuth code. Without this middleware, Google OAuth fails.
3. **Server-side auth helpers**: `src/lib/auth-server.ts` exposes
   `requireUser` / `requireCoach` that read the session from cookies
   and load the user's profile. In demo mode they return `null`.
4. **Client-side tier resolution**: `useMembershipTier(profile)`
   queries the `subscriptions` table and picks the highest-priority
   active membership.
5. **AI provider abstraction**: `src/lib/ai-provider.ts` is the
   single entry point for OpenAI-compatible providers (OpenRouter,
   OpenAI, Gemini, Anthropic, Groq, DeepSeek). Switching providers
   is a config change, not a code change.
6. **Two AI call paths**:
   - `callFreeOpenRouter()` — sequential fallback, used for plans /
     articles / research.
   - `callFreeOpenRouterRace()` — parallel `Promise.any`, used for
     chat and swap (3-8s instead of 18-25s).
7. **No external PDF library**: `src/lib/result-png-export.ts` uses
   Canvas 2D → JPEG → minimal PDF 1.4 — keeps the bundle lean.
8. **i18n without a framework**: `src/lib/i18n.tsx` is a custom
   context provider, no `next-intl` / `react-i18next` dependency.
   The `/ar/*` route group mirrors the English routes.

## 7. Current Project Workflow

1. **Owner or reviewer opens a task** with a Task ID (e.g.
   `MH-DOC-001`) and a clear scope.
2. **Implementation agent** (GML or delegated sub-agent) reads
   `AGENTS.md` and `PROJECT_CONTEXT.md`, then inspects the actual
   source code before changing anything.
3. Agent implements → runs `tsc --noEmit` + `bun run lint` + smoke
   tests → updates docs (`README`, `PROGRESS`, `DEVELOPER_GUIDE`,
   `QA_CHECKLIST`, `SECURITY` as applicable).
4. Agent files a final report (template in `AGENTS.md` §9) including
   every discrepancy found and every assumption made.
5. **Human supervisor** reviews the diff, asks questions if needed,
   approves or rejects.
6. Approved changes are pushed to `origin` and the supervisor is
   notified for production deployment (Vercel).
7. After deployment, the supervisor updates `PROGRESS.md` to mark
   the work done.

### 11.1 The Three-Layer Architecture Principle

The project's AI subsystem will move from the current single-layer
model (everything on Vercel) to a three-layer model:

```
┌──────────────────────────────────────────────────────────────┐
│  Layer 1 — EVO (conversational experience)                   │
│  Fast, interactive, user-facing. Lives on Vercel.            │
│  Does NOT do heavy AI execution.                            │
└──────────────────────────────────────────────────────────────┘
                             ↓ (orchestration only)
┌──────────────────────────────────────────────────────────────┐
│  Layer 2 — Vercel (fast application layer)                    │
│  Next.js frontend, EVO chat widget, light API orchestration,  │
│  receiving + persisting Render results.                      │
└──────────────────────────────────────────────────────────────┘
                             ↓ (delegates heavy work)
┌──────────────────────────────────────────────────────────────┐
│  Layer 3 — Render (heavy AI execution layer)                │
│  Long-running AI jobs: blog pipeline, nutrition plans,       │
│  training plans, regeneration / modification, future heavy  │
│  AI features. No user-facing UI.                             │
└──────────────────────────────────────────────────────────────┘
```

**Architecture principle (one line):**

> **EVO = conversational experience. Vercel = fast application layer.
> Render = heavy AI execution layer.**

### 11.4 Why the change is needed

The current architecture places all AI work on Vercel Hobby. This has
produced several concrete problems documented in `PROGRESS.md`:

1. **Vercel Hobby 60s function cap** forced the blog pipeline to be
   split into 6 separate cron steps (BLOG-PIPELINE-REDESIGN-001 +
   P0-1) just to fit under the limit. Each step is fragile — any
   upstream OpenRouter rate-limit hits the whole pipeline (see
   BLOG-PIPELINE-RESILIENCE-002 production runtime verification: 3
   retry attempts, all failed, 15-minute Step 1 budget consumed).
2. **External research path was discovered broken** —
   `generateExternalResearch()` in `src/lib/blog-generate.ts:446-590`
   uses raw `fetch()` against `https://internal-api.z.ai/v1/functions/invoke`
   with the default `"Z.ai"` API key, which returns `invalid X-Token`
   on every call. Documented as Known Unresolved Issue #1 in
   `AI-RESEARCH-EXTERNAL-001` (PROGRESS.md). A Render Backend would
   not have the 60s cap and could use the `z-ai-web-dev-sdk` directly.
3. **Plan generation (nutrition + training) currently runs in a
   single Vercel function** with `maxDuration=60`. Long generations
   are at risk of timeout. Moving to Render removes this constraint.
4. **EVO is currently coupled to plan generation** via the
   subscriber-gating regex in `src/app/api/ai/chat/route.ts` —
   messages matching plan-generation patterns gate the user to
   `/memberships`. This is correct today (EVO blocks plan requests),
   but a dedicated plan-generation surface will let EVO hand off to
   Render cleanly instead of being a gate.
